# 引き継ぎ（handoff）

他方のAIが、人間からの状況説明なしに作業を再開できる状態を作ってから終了する。

## 実行順序（厳守）

順序を入れ替えないこと。`HANDOFF.md` の更新を push より後に行うと、その更新は commit に含まれず相手に届かない。

### 1. HANDOFF.md を上書き更新する

リポジトリ直下の `HANDOFF.md` を、以下の形式で**上書き**する（追記しない）。20行以内に収める。

```markdown
# HANDOFF

- 更新: YYYY-MM-DD HH:MM JST
- 更新者: Claude Code
- 対象Issue: #12
- 作業ブランチ: claude/xxx
- PR: #13
- 状態: 作業中 | レビュー待ち | 完了

## いま何をしていたか
（1〜3行）

## 次にやること
（箇条書き。最大3つ）

## 詰まっている点・人間の判断が必要な点
（なければ「なし」）
```

Issue・ブランチ・PR番号の3つは必須。再開側はこれを頼りに現場へ到達する。
未作成のものは「なし」と明記し、空欄にしない。

### 2. Issue へ進捗コメント（中断する場合）

対象 Issue に、担当AI・作業ブランチ・現在の状態・次の一手を1コメントで残す。
セッションがどのブランチで始まるかは環境によって変わるため、**Issue だけが確実に読まれる入口**である。

`status:in-progress` ラベルを使っている場合は、このコメントと同時に外す（単独で操作しない）。

### 3. commit

`HANDOFF.md` の変更を必ず含める。

### 4. push

`git push -u origin <branch-name>`。

### 5. PR を作成 / 更新

レビュー可能な状態なら PR を作成、既にあれば説明文を更新する。
設計判断とその理由は PR 説明文に書く（`HANDOFF.md` には履歴を残さない）。
**PR を作らない作業なら、設計判断は対象 Issue のコメントに残す。**

## 書いてはいけないもの

`HANDOFF.md`・Issue・PR は push 済み GitHub 上の共有面である。
実データ、個人情報、認証情報（API キー・トークン・秘密鍵）、社外に出せない業務情報は書かない。
再現に実データが要る場合は、データ本体ではなく取得方法と置き場所を書く。

## GitHub に接続できない場合

Issue の確認・push・PR 更新のいずれかが権限・認証・ネットワークで失敗したら、
**引き継ぎ完了として終了しない。**

1. できたところまで local に commit する
2. どの操作がどんなエラーで失敗したかを人間に報告する
3. 人間の対応を待つ

## チェック

終了前に確認する。

- [ ] `HANDOFF.md` に Issue・ブランチ・PR が書かれているか
- [ ] `HANDOFF.md` が commit に含まれているか
- [ ] push 済みか（`git status` がクリーンか）
- [ ] 作業が未完了でも上記を実行したか
- [ ] 機密情報を書いていないか

未完了を理由に push を省略しない。相手から見れば、push されていない作業は存在しない。
